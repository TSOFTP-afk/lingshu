## 一、落地总原则

### 1.0 当前项目基线（2026-05-23）

落地前必须先承认当前代码已经发生的结构变化，避免方案继续按旧版单体 UI 推进：

- `novel_app.qt_app` 仍是公共入口，保留 `NovelQtMainWindow`、`run_qt_app`、`DRAWER_TAB_SEQUENCE` 等兼容导入。
- 右侧抽屉已拆到 `novel_app/qt/drawer/`：
  - `controller.py` 负责 tab 构建、可见性、打开/刷新分发。
  - `pages.py` 是兼容门面，只转发到具体页面模块。
  - 现有页面模块包括 `overview.py`、`outline.py`、`shortcuts.py`、`characters.py`、`world.py`、`skills.py`、`review.py`、`tasks.py`。
- 当前 `DRAWER_TAB_SEQUENCE` 为：

```python
("overview", "outline", "characters", "world", "skills", "review", "tasks")
```

- 当前 `DrawerController.build_tabs()` 实际还会构建 `shortcuts` tab，位于 `overview` 与 `outline` 之间。后续加入 `analysis` 时必须同步校准兼容常量、实际构建顺序和测试断言，避免只改 `DRAWER_TAB_SEQUENCE` 而漏掉真实 UI 顺序。
- 星图 UI 已从抽屉中下线，不应在新方案中再把 `star` 放回 tab 序列。
- 全书分析主逻辑已随主窗口拆分迁入 `novel_app/qt/app_analysis.py`，`qt_app.py` 只保留主窗口兼容壳；关键方法包括 `_analyze_book_full`、`_start_ai_book_summary`、`_analyze_book_in_batches`、`_filter_untrusted_book_analysis_payload`、`_apply_book_analysis_result`。
- 当前 `_analyze_book_full` 与 `_start_ai_book_summary` 的完成回调都会调用 `_apply_book_analysis_result(book_id, payload)`，这是本方案 P0 必须优先改掉的风险点。
- 右侧“记录”tab 已迁到 `novel_app/qt/drawer/review.py`，分析草案 UI 不应继续塞进 review 页，应新增独立 `analysis.py`。

### 1.0.1 当前落地状态补充（2026-06-01）

- P0 草案闭环已有基础实现：`analysis_runs`、`analysis_cards`、`analysis_audit_logs`、`analysis_apply_snapshots` 已进入数据库迁移，`AnalysisStore` 与分析抽屉 tab 已存在。
- 全书分析完成回调已转向草案保存路径，默认不直接写回正式人物、世界观和章节事件；应用草案时才调用旧写回逻辑并生成快照/审计日志。
- 证据统计与基础门禁已开始下沉到 `novel_app/analysis/evidence.py`，供 diff、草案详情和后续写回门禁复用。
- 纯字符切片已开始替换为 `novel_app/analysis/chunker.py` 的章节/段落感知分块，输出稳定 `block_uid`。
- `analysis_blocks` 已进入数据库迁移与 `AnalysisStore`，全书分析 run 创建后会预生成并保存原文分块，草案 diff 可记录 `evidence_resolution` 回查结果。
- RAG 检索已新增 `doc_types` 过滤参数，并在上下文构建中区分章节、书籍设计、参考书和分析块来源；`ChapterRetriever.index_analysis_block()` 已支持把分析原文块作为 `analysis_block` 索引，降低辅助资料污染正式上下文的风险。
- 应用分析草案前已新增 `evidence_writeback_gate` 复核：实际写回字段必须能通过 `block_uid + quote` 回查到 `analysis_blocks`，`weak/missing` 会被阻止并把完整草案卡标记为 `blocked`。
- 书籍模板 `tag_profile` 已被 `normalize_book_outline_form` 保留并规范化；`TruthManager.build_all()` 已能把已保存的父标签、子标签、自定义标签和备注写入 `current_state.md` 的“书籍标签画像”，空画像或删除后的标签不会残留。

### 1.1 先保护现有能力

灵枢当前已经有可用的全书三级分析流程、人物/世界观写回、章节事件写回、Truth File、RAG 和多 Agent 审查。下一代分析系统第一阶段必须遵守：

- 不删除现有 `_analyze_book_in_batches` 能力。
- 不删除现有 `_apply_book_analysis_result`，但改变其调用入口。
- 不让“AI 分析全书”默认覆盖正式人物卡、世界观和章节事件。
- 新增功能默认走草案层，用户确认后才写回。
- 所有新增表必须兼容旧数据库，无需用户手工迁移。

### 1.2 先做最小闭环

第一阶段只做最有价值、风险最小的闭环：

```text
现有全书三级分析
  -> 生成分析草案 analysis_cards
  -> 生成 diff_json
  -> UI 展示草案和差异
  -> 用户确认
  -> 调用现有写回逻辑
  -> 记录审计日志
```

暂时不在第一阶段实现完整实体共指、别名演化图、假设性回溯和外部向量库。

### 1.3 保持双轨运行

短期内保留两条路径：

| 路径 | 用途 | 默认状态 |
|------|------|----------|
| 旧路径：分析后直接写回 | 兼容已有能力、调试兜底 | 隐藏或作为高级选项 |
| 新路径：分析后生成草案 | 正式用户路径 | 默认启用 |

推荐加一个内部开关：

```python
BOOK_ANALYSIS_DRAFT_MODE = True
```

或者复用设置项，允许用户在调试时回退旧路径。

## 三、第一阶段 MVP 范围

### 3.1 MVP 要解决的问题

MVP 只解决当前最危险的问题：全书分析结果会直接覆盖正式数据。

MVP 完成后，用户流程变为：

```text
点击“AI 分析全书”或“AI 总结全书”
  -> 后台运行现有三级分析
  -> 结果写入 analysis_runs / analysis_cards
  -> 右侧打开“分析”Tab
  -> 用户查看书籍、人物、世界观、章节事件草案
  -> 用户点击“应用”
  -> 系统创建快照/审计日志
  -> 调用现有写回逻辑写入正式数据
```

### 3.2 MVP 不解决的问题

以下内容暂不进入第一阶段：

- 完整实体共指消解。
- `analysis_entities` / `analysis_mentions` 的完整生产流程。
- ARS 精准计算。
- 块级 RAG 索引。
- 单章修改后的自动局部重算。
- 复杂差异合并 UI。

第一阶段可以先把一整个全书分析结果视为一张或多张草案卡：

| 草案卡 | 内容来源 |
|--------|----------|
| `book_summary` | `book_outline`、`book_outline_form` |
| `world` | `world_form`、`world_entries`、`world_text` |
| `characters` | `characters` 数组 |
| `chapters` | `chapter_updates` |
| `unresolved` | `analysis_unresolved` |

### 3.3 MVP 验收标准

- 全书分析完成后不再自动修改 `characters`、`books.world_data_json`、`chapter_events`。
- “AI 分析全书”和“AI 总结全书”两个入口都必须满足上一条。
- 分析结果能在重启后继续查看。
- 用户点击“应用草案”后，才执行现有正式写回。
- 应用前后写入 `analysis_audit_logs`。
- 旧的直接写回路径可作为内部兜底，但默认不可触发。

## 四、数据库落地方案

### 4.1 P0 必须新增的表

P0 先新增四张表：

1. `analysis_runs`
2. `analysis_cards`
3. `analysis_audit_logs`
4. `analysis_apply_snapshots`

`analysis_blocks` 可以 P1 再接入。P0 如果暂时沿用现有三级分析结果，不强依赖分块持久化。

### 4.2 `analysis_runs`

```sql
CREATE TABLE IF NOT EXISTS analysis_runs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    book_id INTEGER NOT NULL,
    scope_type TEXT NOT NULL DEFAULT 'book',
    status TEXT NOT NULL DEFAULT 'created',
    pipeline_version TEXT NOT NULL DEFAULT 'draft_mvp_v1',
    input_hash TEXT NOT NULL DEFAULT '',
    summary TEXT NOT NULL DEFAULT '',
    error_text TEXT NOT NULL DEFAULT '',
    meta_json TEXT NOT NULL DEFAULT '{}',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    completed_at DATETIME,
    FOREIGN KEY (book_id) REFERENCES books(id) ON DELETE CASCADE
);
```

### 4.3 `analysis_cards`

```sql
CREATE TABLE IF NOT EXISTS analysis_cards (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    book_id INTEGER NOT NULL,
    run_id INTEGER NOT NULL,
    card_uid TEXT NOT NULL,
    card_type TEXT NOT NULL,
    entity_uid TEXT NOT NULL DEFAULT '',
    card_version INTEGER NOT NULL DEFAULT 1,
    ars_score REAL NOT NULL DEFAULT 0.0,
    status TEXT NOT NULL DEFAULT 'draft',
    payload_json TEXT NOT NULL,
    diff_json TEXT NOT NULL DEFAULT '{}',
    applied_table TEXT NOT NULL DEFAULT '',
    applied_id INTEGER,
    applied_at DATETIME,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (book_id) REFERENCES books(id) ON DELETE CASCADE,
    FOREIGN KEY (run_id) REFERENCES analysis_runs(id) ON DELETE CASCADE,
    UNIQUE(run_id, card_uid)
);
```

## 六、全书分析接入改造

### 6.1 当前关键路径

当前路径是：

```text
_analyze_book_full
  -> _analyze_book_in_batches
  -> done(payload)
  -> _apply_book_analysis_result(book_id, payload)
```

同时还存在第二个入口：

```text
_start_ai_book_summary
  -> _analyze_book_in_batches
  -> done(payload)
  -> _apply_book_analysis_result(book_id, payload)
```

需要改为：

```text
_analyze_book_full / _start_ai_book_summary
  -> create_analysis_run
  -> _analyze_book_in_batches
  -> done(payload)
  -> save_book_analysis_draft(run_id, payload)
  -> _open_drawer("analysis")
  -> _refresh_analysis_tab()
```

### 6.2 `_analyze_book_full` / `_start_ai_book_summary` 修改点

当前两个入口的 `done(payload)` 都直接写回。P0 必须同时改造，不能只改工具栏里的“分析全书”，否则“AI 总结全书”仍会绕过草案层。

目标：

```python
def done(payload: Any) -> None:
    if not isinstance(payload, dict):
        return
    run_id = self.database.create_analysis_run(book_id, meta={...})
    card_ids = self._save_book_analysis_draft(book_id, run_id, payload)
    self.database.update_analysis_run_status(run_id, "awaiting_review", summary=f"生成 {len(card_ids)} 张分析草案")
    self._open_drawer("analysis")
    self._refresh_analysis_tab()
```

更稳妥的做法是在后台开始前创建 `run_id`，失败时能更新状态：

```text
created -> running -> awaiting_review / failed / cancelled
```

两个入口建议共用同一个私有方法：

```python
def _handle_book_analysis_payload_as_draft(self, book_id: int, run_id: int, payload: dict[str, Any]) -> None:
    ...
```

这样可以把状态更新、草案保存、抽屉打开和日志写入集中到一处，减少遗漏第二入口的风险。

### 6.3 新增 `_save_book_analysis_draft`

建议先放在 `qt_app.py`，后续迁到 `analysis/pipeline.py`。

职责：

- 调用 `split_book_analysis_payload(payload)`。
- 为每张草案补 diff。
- 写入 `analysis_cards`。
- 写入一条 `analysis_audit_logs(action="draft_created")`。

P0 为降低应用风险，建议额外保存一张 `card_type="full_payload"` 的完整草案卡，或在 run 的 `meta_json` 中保存完整原始 payload 摘要引用。这样即使细粒度拆卡 diff 还不完美，“应用整次运行”仍可复用现有写回逻辑。

### 6.4 `_apply_book_analysis_result` 改职责

保留函数主体，但重命名或包一层：

```python
def _apply_confirmed_book_analysis_result(self, book_id: int, payload: dict[str, Any], *, run_id: int | None = None) -> None:
    ...
```

或者保留原名，但增加注释和调用约束：

```python
def _apply_book_analysis_result(...):
    """Only call after user explicitly confirms an analysis draft."""
```

关键点：

- 不能再由 `_analyze_book_full.done` 直接调用。
- 也不能再由 `_start_ai_book_summary.done` 直接调用。
- 应用前必须创建 `analysis_apply_snapshots`。
- 应用后必须标记卡片 `applied`。
- 应用后必须写审计日志。

P0 的确认应用粒度建议收缩为：

| 应用粒度 | P0 状态 | 原因 |
|----------|---------|------|
| 应用整次运行 / 完整 payload | 默认支持 | 可最大化复用现有 `_apply_book_analysis_result`，风险最低 |
| 应用全部可写回卡片 | 可支持，但内部仍可合并为完整 payload | UI 文案友好，工程上不必立刻做字段级 patch |
| 应用单张细粒度卡片 | 谨慎开放 | 只有 `book_summary/world/characters/chapters` 等映射足够明确时再启用 |
| 字段级勾选应用 | 暂缓 | 需要更细 diff、证据和冲突处理，容易拖慢 P0 |

### 6.5 旧路径兜底

可以保留一个隐藏调试方法：

```python
def _apply_book_analysis_result_legacy_direct(...)
```

或者设置项：

```python
if not self.book_analysis_draft_mode:
    self._apply_book_analysis_result(book_id, payload)
```

默认必须为草案模式。

#### 布局位置

章节标签栏放在主编辑区上方、工具按钮下方：

新增轻量会话对象：

```python
@dataclass

    chapter_id: int
    title: str
    outline_text: str
    content_text: str
    summary_text: str = ""
    dirty: bool = False
    cursor_position: int = 0
    scroll_position: int = 0
```

主窗口持有：

```python

self.open_chapter_order: list[int]
self.active_chapter_session_id: int | None
```

P1 可以先共享一套 `chapter_outline_editor/content_editor`，切 tab 时保存当前编辑器内容到 session，再把目标 session 内容加载进编辑器。P2 已升级为每个 tab 拥有独立 editor widget，激活时切换 stack 并重定向当前编辑器属性。

当前落地状态：`ChapterTabsController` 和 `ChapterEditorSession` 已进入 `novel_app/qt/chapter_tabs.py`；左侧目录点击章节会复用已打开 tab 或创建新 tab，tab 切换会保存/恢复正文、章节梗概、光标、滚动条和 dirty 状态；`Ctrl+S` 保存当前 tab，`Ctrl+Shift+S` 与“保存全部”按钮保存所有 dirty tab；删除章节会清理对应 tab/session；搜索命中章节时会直接切换/打开对应 tab；AI 写回、审查快照恢复和全书分析写回会刷新打开的干净 tab，并避开后台 dirty tab 的自动覆盖。

P1 控制器接口建议：

```python
class ChapterTabsController:
    def open_chapter(self, chapter_id: int) -> None: ...
    def close_chapter(self, chapter_id: int) -> bool: ...
    def activate_chapter(self, chapter_id: int) -> None: ...
    def save_current_session(self) -> bool: ...
    def save_all_sessions(self) -> bool: ...
    def mark_current_dirty(self, dirty: bool = True) -> None: ...
```

主窗口需要把 `_load_chapter(chapter_id)` 拆成两层：

- `open_chapter_tab(chapter_id)`：面向 UI、树点击、搜索跳转，负责复用已打开 tab。
- `_load_chapter_into_editor(chapter_id)`：只做数据库读取和编辑器填充，不再隐式创建或覆盖其他会话。

这样可以避免当前 `_load_chapter` 每次调用 `_load_book(...)` 时重置书籍状态、刷新侧栏数据，并意外冲掉其他打开章节的未保存会话。

#### 交互规则

- 左侧目录点击章节：
  - 如果章节已打开，切换到对应 tab。
  - 如果未打开，创建新 tab 并加载章节。
- tab 标题：
  - 未修改：`第12章 夜航`
  - 已修改：`● 第12章 夜航`
  - 模板章节：可在前缀显示 `★`
- 关闭 tab：
  - 无修改：直接关闭。
  - 有修改：弹出 `保存 / 放弃 / 取消`。
- 保存：
  - `Ctrl+S` 保存当前 tab。
  - 可增加“保存全部”用于所有 dirty tabs。
- 删除章节：
  - 如果被删除章节已打开，关闭对应 tab 并清理 session。
- 任务写回：
  - 长篇生成、润色、AI 审查写回前检查目标章节 tab 是否仍打开且 dirty。
  - 如果目标 tab 被用户改动，按当前 `_is_job_target_dirty` 思路跳过自动覆盖或提示用户确认。

#### 测试点

- 打开同一章节不会重复创建 tab。
- 切换 tab 会保存并恢复正文、大纲、光标位置。
- dirty tab 关闭时必须询问。
- 删除章节会关闭对应 tab。
- `Ctrl+S` 只保存当前 tab，“保存全部”保存所有 dirty tabs。

### 7.12 润色功能改为仅润色选区

当前 `_start_generation("polish")` 的行为接近整章润色，且会清空/替换正文编辑器内容。新需求要求：每次润色只处理用户在正文编辑器中选中的片段。

P0/P1 并行可做，建议优先级高于复杂章节多标签，因为它能直接降低误覆盖风险。

#### 新行为

- 用户必须先在正文编辑器中选中一段文本。
- 点击 `润色` 后，只把选中文本发送给 AI。
- AI 返回润色结果后，只替换原选区。
- 未选中文本时，不启动任务，提示：

```text
请先选中需要润色的正文片段。
```

#### 上下文策略

AI 输入包含：

- `selected_text`：必须润色的文本。
- `before_context`：选区前最多 800-1200 字，只作语境参考。
- `after_context`：选区后最多 800-1200 字，只作语境参考。
- 章节大纲、Truth File、Skills、sourcebook/RAG 上下文。

提示词必须明确：

```text
只润色【选中文本】。
不要续写选区之外的内容。
不要输出解释。
不要输出 before_context 或 after_context。
```

#### UI 流程

```text
用户选中正文片段
  -> 点击“润色”
  -> 创建“选区润色前快照”
  -> 任务面板显示进度
  -> 返回后弹出选区对照
  -> [接受] 仅替换原选区
  -> [放弃] 保持全文不变
```

对照弹窗只展示选区：

```text
┌──────────────────────┬──────────────────────┐
│ 原选区                │ 润色后                │
├──────────────────────┼──────────────────────┤
│ ...                  │ ...                  │
└──────────────────────┴──────────────────────┘
[接受替换选区] [复制润色结果] [放弃]
```

#### 需要改造的方法

```python
def _selected_content_range(self) -> tuple[int, int, str] | None: ...
def _start_polish_selection(self) -> None: ...
def _show_polish_selection_diff_dialog(self, job: dict[str, Any]) -> None: ...
def _replace_content_range(self, start: int, end: int, replacement: str) -> None: ...
```

`_start_generation("polish")` 可以改为直接委托：

```python
if mode == "polish":
    self._start_polish_selection()
    return
```

任务 job 需要记录：

```python
{
  "mode": "polish",
  "polish_scope": "selection",
  "selection_start": start,
  "selection_end": end,
  "selected_text": selected_text,
  "base_content": full_content_before,
}
```

实现时要特别避开当前流式写入正文的路径：

- 不再把润色任务标记为 `target = "content"`。
- 建议使用 `target = "polish_preview"` 或 `target = "log"`，让 `_on_ai_chunk` 只累积 `job["result_text"]`，不写入 `content_editor`。
- `_on_ai_done` 在 `mode == "polish"` 时打开选区对照弹窗，用 `job["result_text"]` 作为润色后文本。
- 只有用户点击“接受替换选区”后，才修改 `content_editor` 并标记 dirty。

如果保留旧 `_show_polish_diff_dialog`，它也必须只从 `job["selected_text"]` 和 `job["result_text"]` 取值，不能再读取整个 `content_editor.toPlainText()` 作为“润色后”。

接受替换前要验证：

- 当前章节仍是目标章节。
- 当前正文在选区附近未发生冲突修改。
- 如果全文已改变但原选区范围仍可定位，提示用户确认；无法定位则只把润色结果放入弹窗，不自动替换。

- `穿越` 父标签先作为可选分区存在，即使当前映射文件没有独立子标签段，也允许用户选择穿越相关子标签或自定义标签。
- 已选标签保存到书籍级模板后才被视为正式选择；只在搜索结果中浏览不进入 Truth。

- 用户保存书籍级模板时，`tag_profile` 随 `outline_data_json` 入库。
- 保存成功后调用现有 Truth 同步路径时，已选标签进入 Truth 的“书籍标签画像”。
- 用户取消选择或删除自定义标签并保存后，下次 Truth 同步应移除对应标签。

### 7.15 UI 美化重构架构方案

UI 美化重构采用 **PyQt6 渐进式重构**。目标不是一次性换皮，而是在保留现有写作、分析、Truth、任务和抽屉能力的前提下，把界面整理成可长期维护的写作工作台。

视觉方向采用 **强视觉风格**，但必须服务于长时间写作：高可读、高密度、稳定交互、状态明确。主题策略采用 **保留并收敛**：继续保留白色、浅色、深色、护眼和背景图能力，但统一 token、组件状态和页面结构。

架构分为四层：

| 层级 | 职责 | 落地方式 |
|------|------|----------|
| App Shell | 管理主窗口骨架、全局状态、页面切换和抽屉挂载 | 从 `NovelQtMainWindow` 中渐进抽出 `AppShell`、`HeaderBar`、`LibrarySidebar`、`WorkspaceStack`、`RightDrawerHost`、`StatusStrip` |
| Page | 承载书库、章节编辑、书籍级模板、分析、任务、Truth 等业务页面 | 页面只组织组件和转发事件，不直接写数据库 |
| Component | 提供统一按钮、搜索框、标签、表单行、列表项、徽标、空状态、提示组件 | 组件只负责显示、状态和信号，不直接访问业务服务 |
| Theme | 统一颜色、间距、圆角、字体和控件状态 | 由主题 token 生成基础 QSS、组件 QSS、页面 QSS |

主窗口拆分目标：

| 组件 | 说明 |
|------|------|
| `AppShell` | 三栏工作台外壳，组合 Header、左侧书库、中间工作区、右侧抽屉和底部状态 |
| `HeaderBar` | 当前书籍状态、全局搜索、主题入口、保存/同步状态、抽屉入口 |
| `LibrarySidebar` | 书库和章节导航，使用高密度列表项展示书名、章节数、最近编辑状态 |
| `WorkspaceStack` | 空状态、章节编辑、书籍级模板、多章节 tab 等主工作区页面 |
| `RightDrawerHost` | 统一承载 overview、outline、characters、world、skills、analysis、review、tasks 等抽屉页 |
| `StatusStrip` | 后台任务、保存状态、Truth/RAG 同步状态、错误提示 |

统一组件库：

| 组件 | 用途 |
|------|------|
| `LxButton` | `primary`、`secondary`、`ghost`、`danger`、`icon` 等按钮状态 |
| `LxSearchBox` | 书库搜索、抽屉搜索、书籍级模板标签搜索 |
| `LxSegmentedTabs` | 页面内模式切换，替代零散按钮组 |
| `LxPanel` | 普通面板，圆角控制在 8px 以内，避免卡片套卡片 |
| `LxSection` | 表单分组标题、说明和右侧操作按钮 |
| `LxFormRow` | 表单标签、输入控件、提示、错误状态统一布局 |
| `LxTagChip` | 内嵌标签、自定义标签、已选标签、Truth 启用状态 |
| `LxListItem` | 书籍、章节、任务、分析卡、参考书统一列表项 |
| `LxBadge` | 状态、数量、风险等级、Truth/RAG 同步状态 |
| `LxToast` / `LxInlineAlert` | 保存成功、校验失败、后台任务结果 |
| `LxEmptyState` | 空书库、空章节、空分析结果、空参考书 |

主题 token 必须覆盖：

- `color`：背景、面板、文本、弱文本、边框、主色、强调色、危险色、成功色、选中态。
- `spacing`：4、8、12、16、24、32。
- `radius`：4、6、8；普通卡片和面板不得继续扩大圆角。
- `typography`：标题、正文、辅助文本、表单标签、状态数字。
- `state`：hover、pressed、focus、disabled、selected。

视觉约束：

- 强视觉风格只通过主题、图标、层级、状态色和细节质感体现，不做营销页式大图或装饰背景。
- 书籍级模板、抽屉、书库、章节编辑器都应保持信息密度和可扫描性。
- 背景图模式继续支持，但文字区域必须保持足够对比度，不能影响长时间阅读。
- 不新增孤立样式；所有新页面优先复用组件库和主题 token。

书籍级模板标签栏与 `7.14` 保持一致：

- 标签栏使用 `LxSearchBox` + `LxTagChip` + 可滚动结果列表。
- 输入文字后按相似度检索内嵌标签库。
- 结果最后一行永远显示自定义标签入口。
- 已选标签展示 Truth 启用状态；自定义标签用独立 chip 状态区分。
- 组件层只发出选择、删除、自定义确认等信号，Truth 写入仍由书籍模板保存与同步流程负责。

抽屉系统统一规则：

- tab 使用统一图标、短标签、选中态和 hover 态。
- 每个抽屉页统一标题栏、刷新状态、加载状态、空状态和错误提示。
- `review`、`tasks`、`analysis` 等信息量大的页面可继续触发宽抽屉。
- 抽屉页只组织 UI 和转发事件，不直接持久化复杂业务。

实施顺序：

1. 先收敛主题 token，把现有大段 QSS 拆为基础样式、组件样式、页面样式。
2. 再落地组件库，优先实现按钮、搜索框、面板、表单行、标签 chip、列表项、徽标、空状态。
3. 然后替换 Header、左侧书库、右侧抽屉、书籍级模板四个高频区域。
4. 最后从 `qt_app.py` 渐进拆分主窗口 UI 构建职责，保留兼容 wrapper，避免业务链路大迁移。

## 九、RAG 与 Truth File 接入

### 9.1 RAG / Truth / Evidence 治理链

新增统一治理链：

```text
原文 / RAG / 参考书
  -> EvidenceRef
  -> 证据门禁
  -> analysis_cards 草案
  -> 用户确认写回
  -> Truth File / RAG 同步刷新
```

上下文优先级固定为：

```text
用户当前明确指令 > Truth File > 正式书籍数据 > RAG 正式资料 > 参考书基础数据 > 分析草案
```

关键原则：

- Truth File 只代表已确认事实，不能读取未确认 `analysis_cards` 作为事实来源。
- RAG 结果必须带 `doc_type`，不能把参考书、分析草案、正式设定混在同一上下文段落里。
- 证据门禁的最终拦截点在“确认写回”之前，不依赖提示词自觉。
- 草案可以展示“候选 Truth 更新”，但确认写回前不得进入 Truth 文件。
- 写回成功后统一触发 `_sync_truth_files(book_id)`，并刷新相关 RAG 索引。

### 9.2 RAG 来源分层

RAG payload 必须显式区分来源：

| doc_type | 来源 | 可否进入 Truth | 主要用途 |
|----------|------|----------------|----------|
| `chapter_summary` | 已保存章节摘要/正文片段 | 间接，需用户确认 | 生成、审查、原文回查 |
| `book_design` | 已确认书籍级结构化设定 | 是 | 生成、审查、聊天上下文 |
| `analysis_block` | 分析用原文分块 | 否 | evidence refs、source_requests 回查 |
| `book_reference` | 书籍级参考书 | 否 | 风格/设定参考、RAG 辅助 |
| `truth_snapshot` | 已生成 Truth File 快照 | 是 | 快速检索已确认状态 |

`ChapterRetriever.search(...)` 增加 `doc_types` 参数：

```python
def search(
    self,
    book_id: int,
    query: str,
    top_k: int = 8,
    *,
    doc_types: set[str] | None = None,
    use_hybrid: bool = True,
    use_rerank: bool = False,
) -> list[dict[str, Any]]: ...
```

实现要求：

- 向量检索要把 `doc_types` 转换为底层 `filter_condition`，或在结果返回后统一过滤。
- BM25 检索也必须应用相同 `doc_types` 过滤，不能只过滤向量结果。
- `_merge_results` 之后再做一次最终过滤，防止混合排序把错误来源重新带回结果。
- 旧章节点如果没有 `doc_type`，按 `chapter_summary` 处理；新增索引应显式写入 `doc_type`。

`build_context_from_results(...)` 按来源分区输出：

```text
【RAG：正式书籍资料】
- 书籍级设定：...

【RAG：原文回查片段】
- 第 12 章 / block_uid=...：...

【RAG：参考书基础数据】
- [文风参考]《参考书名》第 3 段：...
```

### 9.3 P1 新增块索引

在 `ChapterRetriever` 中新增：

```python
def index_analysis_block(self, book_id: int, block_uid: str, chapter_id: int, summary: str, content_snippet: str, metadata: dict | None = None) -> None: ...
def remove_analysis_blocks_for_chapter(self, book_id: int, chapter_id: int) -> None: ...
```

当前落地状态：上述两个接口已加入 `novel_app/rag/retriever.py`；全书分析入口会在 run 创建后保存 `analysis_blocks`，并把可索引 block 以 `doc_type="analysis_block"` 写入 RAG。草案 diff 中的 `evidence_resolution` 会用 `block_uid + quote` 回查原文块，后续写回门禁可直接复用该结果。

写回门禁当前落地状态：`novel_app/analysis/diff_apply.py::evidence_writeback_gate` 会忽略 `analysis_unresolved`、source request 和 `_meta` 等非写回字段，只检查实际将进入正式数据的 payload；`novel_app/qt/app_drawer.py::_apply_confirmed_analysis_run` 在调用 `_apply_book_analysis_result` 前会再次重算门禁，阻止旧草案或过期 diff 绕过。

payload 使用：

```json
{
  "doc_type": "analysis_block",
  "book_id": 1,
  "chapter_id": 12,
  "block_uid": "BOOK-1:CH-12:B-0002:abcd1234",
  "summary": "...",
  "content_snippet": "..."
}
```

`block_uid` 必须稳定，推荐格式：

```text
BOOK-{book_id}:CH-{chapter_id}:B-{block_index:04d}:{content_hash[:8]}
```

用途：

- 作为 `EvidenceRef.block_uid`。
- 作为 `source_requests` 原文回查定位。
- 作为后续重跑分析时的增量判断依据。

### 9.4 书籍级参考书 RAG 接入

书籍级参考书导入后，P1 可以直接进入 RAG，但必须限定作用域：

```json
{
  "doc_type": "book_reference",
  "book_id": 1,
  "source_id": 8,
  "segment_index": 12,
  "role": "style_reference",
  "title": "参考书第 3 章",
  "content_snippet": "..."
}
```

检索规则：

- 只检索当前书籍绑定且 enabled 的参考书。
- 参考书结果在 `sourcebook_context` 中单独分区展示，不与正式设定混写。
- 生成、润色、审查可读取参考书；全书分析 P0 不强依赖参考书，P1 后可作为辅助上下文。
- 删除或解绑参考书时，必须同步移除对应 `doc_type = "book_reference"` 的向量记录。

当前已在 `ChapterRetriever` 明确定义参考书稳定 point id；`QdrantLocalClient.delete_by_filter()` 可按 `doc_type + book_id + source_id` 批量删除，也支持按分段 point id 精确删除：

```python
point_id = f"book_reference:{source_id}:{segment_index}"
```

已新增方法：

```python
def index_book_reference_segments(self, book_id: int, source_id: int, segments: list[dict[str, Any]]) -> None: ...
def remove_book_reference_source(self, book_id: int, source_id: int, segment_indexes: list[int] | None = None) -> None: ...
def search(self, book_id: int, query: str, top_k: int = 8, *, doc_types: set[str] | None = None, use_hybrid: bool = True, use_rerank: bool = False) -> list[dict[str, Any]]: ...
```

`build_context_from_results` 已增加 `doc_type == "book_reference"` 分支，输出示例：

```text
- 参考书[文风参考]《舰长的崩坏日常》第 3 章：...
```

禁用参考书时有两种选择：

- 简单方案：同步调用 `remove_book_reference_source(...)` 删除向量和 BM25 记录。
- 保留缓存方案：payload 写入 `enabled/source_id/role`，检索时增加 `doc_types` 和 enabled source id 过滤；这需要扩展混合检索的 BM25 过滤逻辑。

### 9.5 Truth File 接入强化

P0 仍不改变 Truth File 的事实来源：只有用户确认写回后的正式数据才能进入 Truth。

新增“候选 Truth 更新”概念：

```json
{
  "candidate_truth_updates": [
    {
      "truth_file": "current_state.md",
      "section": "人物总览",
      "subject": "林一",
      "change_summary": "补充能力来源",
      "evidence_status": "trusted"
    }
  ]
}
```

规则：

- `candidate_truth_updates` 只展示在分析草案详情中，不写入 Truth 文件。
- 应用分析卡前再次执行证据门禁；`weak/missing` 不得进入 Truth。
- 应用成功后调用 `_sync_truth_files(book_id)`。
- 如果写回内容影响章节摘要、人物、世界观或书籍大纲，同步刷新相关 RAG 索引。
- Truth 上下文在 AI 输入中独立分区，并标注“必须优先遵守”。
- 书籍级模板中的 `tag_profile` 属于用户已确认的正式书籍数据；用户保存模板后，已选父标签、子标签和自定义标签应进入 `current_state.md` 的“书籍标签画像”。
- 未被用户选择的内嵌标签库条目不进入 Truth；搜索列表、候选推荐、未保存自定义输入都不能进入 Truth。
- 删除标签或取消选择后，下一次 `_sync_truth_files(book_id)` 必须让 Truth 中的标签画像与当前书籍模板保持一致。

P2 已将确认后的 Truth 文件集合以 `doc_type="truth_snapshot"` 索引到 RAG；来源只取 `_sync_truth_files(book_id)` 后 `TruthManager.build_all()` 生成的正式 Truth 内容，不能用未确认草案生成 `truth_snapshot`。

## 十三、风险与回滚策略

### 13.1 风险：写回路径误触发

风险：

- `_analyze_book_full` 或 `_start_ai_book_summary` 完成后仍误调用旧 `_apply_book_analysis_result`。

控制：

- 增加测试断言。
- `_apply_book_analysis_result` 增加注释和可选参数 `confirmed=True`。
- 未确认调用时抛错或写警告。
- 测试需要同时覆盖两个入口，不能只检查 `_analyze_book_full.done`。

### 13.2 风险：分析草案无法应用

风险：

- 草案卡拆分后 payload 结构与旧写回函数不兼容。

控制：

- P0 草案卡保留原始完整 payload。
- “应用全部”时可直接将完整 payload 传给旧写回函数。
- 细粒度卡片应用后续再做。

### 13.3 风险：快照不完整

风险：

- 应用后用户想回滚，但快照缺字段。

控制：

- `analysis_apply_snapshots` 第一阶段保存全量相关正式数据。
- 不只依赖 `chapter_snapshots`。

### 13.4 风险：UI 复杂度扩大

风险：

- 新分析 Tab 过复杂，拖慢落地。
- UI 美化重构如果一次性重写主窗口，容易牵动写作、抽屉、模板、Truth、任务等业务链路。
- 组件库如果混入业务逻辑，会让页面职责更难拆，后续维护成本上升。

控制：

- 第一阶段只做列表 + 文本预览 + 应用按钮。
- 精细 diff、字段级勾选、颜色状态后续迭代。
- UI 美化重构按“主题 token -> 组件库 -> Header/书库/抽屉/书籍级模板 -> `qt_app.py` 渐进拆分”的顺序推进。
- 组件只负责显示、状态和信号，不直接访问数据库、Truth、RAG 或 AI 服务。
- 保持现有控制器和数据服务不变，页面层只做事件转发和状态呈现。
- 每轮替换都保留回退点：旧页面或旧 wrapper 在新组件通过 smoke test 前不删除。

### 13.5 风险：选区润色范围漂移

风险：

- AI 返回结果时用户已经继续编辑正文，原选区范围不再可信。

控制：

- 启动润色时保存 `base_content`、`selection_start`、`selection_end` 和 `selected_text`。
- 接受结果前校验当前范围文本是否仍等于原选区。
- 校验失败时提示用户重新选择，不自动替换。

### 13.6 风险：章节多标签保存状态混乱

风险：

- 多个章节同时打开后，保存、关闭、AI 写回可能误作用到非当前 tab。

控制：

- 所有编辑动作必须带 `chapter_id` 或当前 `ChapterEditorSession`。
- 关闭脏 tab 前强制确认；删除章节时同步关闭对应 tab。
- AI 任务完成写回前校验目标章节仍存在，且用户未做冲突编辑。

### 13.7 风险：参考书污染正式设定

风险：

- 参考书内容被误当成当前作品正式设定，导致人物、世界观或章节分析写回错误。

控制：

- 参考书上下文单独标记为“参考书基础数据”，不并入正式书籍资料。
- 写回正式数据仍走分析草案、确认应用和审计日志。
- RAG 检索必须按 `book_id + doc_type = book_reference` 过滤。

### 13.8 风险：标签画像污染 Truth

风险：

- 内嵌标签库或搜索候选被整体写入 Truth，导致 AI 把未选择标签当成当前作品事实。
- 自定义标签与内嵌标签混淆，后续生成或审查误判来源。

控制：

- 只有用户保存到 `tag_profile` 的父标签、子标签和自定义标签能进入 Truth。
- 内嵌库、搜索候选、相似推荐和未保存输入不得进入 Truth。
- 自定义标签进入 Truth 时必须标记 `source=user_custom`。
- 删除或取消选择标签后，下一次 Truth 同步必须移除对应标签。

### 13.9 风险：RAG 污染正式上下文

风险：

- RAG 混合检索把 `book_reference`、`analysis_block`、`book_design` 混成同一段上下文，AI 将辅助资料当成正式事实。

控制：

- RAG payload 必须带 `doc_type`。
- `search(..., doc_types=...)` 按任务显式过滤来源。
- `build_context_from_results` 按来源分区输出，参考书和分析块不得进入“正式设定”分区。

### 13.10 风险：Truth File 滞后

风险：

- 用户确认写回后，Truth File 或 RAG 仍停留在旧状态，后续生成/审查读取到过期事实。

控制：

- 所有正式写回路径统一调用 `_sync_truth_files(book_id)`。
- 影响书籍设计、章节摘要、人物或世界观时同步刷新对应 RAG point。
- 测试覆盖“应用分析卡后 Truth/RAG 刷新”。

### 13.11 风险：证据引用无法回查

风险：

- `evidence_refs` 只有自然语言描述，无法定位到原文块、RAG point 或参考书段落。

控制：

- `EvidenceRef` 至少包含 `source_type/source_id/block_uid/quote/locator`。
- `analysis_block` 使用稳定 `block_uid`。
- 写回前校验 evidence ref 能定位原始 block 或 quote；无法定位降级为 `weak` 或 `missing`。

### 13.12 风险：未确认草案进入 Truth

风险：

- 分析草案中的推断被提前写入 Truth File，导致后续上下文把猜测当事实。

控制：

- Truth 只读取正式数据，不读取未应用 `analysis_cards`。
- 草案只允许提供 `candidate_truth_updates` 预览。
- 只有用户确认应用成功后，才刷新 Truth File。

### 13.13 回滚策略

如果 P0 上线后出现问题：

1. 保留新增表，不删除用户数据。
2. 将 `BOOK_ANALYSIS_DRAFT_MODE` 设为 `False` 可临时恢复旧路径。
3. 使用 `analysis_apply_snapshots` 手动恢复最近一次应用前状态。
4. 新分析 Tab 可隐藏，不影响写作、审查、RAG 和导出。

## 十四、补充功能落地方案

本节汇总本轮新增的三个功能点，作为实际编码时的最小闭环。它们都应遵守“先保护作者文本，再增强 AI 能力”的原则。

### 14.1 章节多标签

目标是让章节编辑像浏览器标签一样工作：同一时间打开多个章节，用户可以快速切换、关闭、保存当前章节或保存全部章节。

落地方式：

- 已新增 `ChapterTabsController` 管理打开顺序、当前 tab、脏状态、关闭确认和保存状态。
- P1 已新增 `QTabBar` 并复用当前主编辑器控件，tab 切换时把当前章节内容保存到会话，再加载目标会话。
- 章节树点击和搜索结果跳转统一调用 `_open_chapter_tab(chapter_id)`；AI 写回、审查快照恢复和全书分析写回统一调用 `_sync_chapter_tab_after_external_write()` 同步已打开 tab。
- tab 标题用 `●` 表示未保存，不改变章节真实标题；“保存全部”和 `Ctrl+Shift+S` 会保存所有 dirty tab。

### 14.2 选区润色

润色功能改为严格选区级操作：用户没有选中正文时不润色，用户选中哪一段就只润色哪一段。

落地方式：

- `_start_generation("polish")` 不再走整章正文流程，而是委托 `_start_polish_selection()`。
- AI 输入只把 `selected_text` 作为目标文本，章节梗概、前后文、Truth、Skills、参考书只作为上下文。
- AI 结果只进入 `job["result_text"]`，不再流式写入正文编辑器。
- 润色完成后弹出“原选区 / 润色后选区”对比框。
- 用户接受后调用 `_replace_content_range(start, end, polished_text)`，拒绝则不修改正文。

### 14.3 书籍级参考库

参考书作为当前书籍的基础数据来源，但不等同于正式设定。它主要服务于生成、润色、审查和后续全书分析。

落地方式：

- 数据库新增书籍到参考来源的绑定表，以及书籍作用域下的参考书分段表。（已落地）
- 导入时复用现有 `reference_sources` 和 `references/imported_books` 存储，再建立当前书籍绑定。（数据接口和 UI 已落地）
- 分段表增加唯一约束和 `content_hash`，重新分段时替换旧分段而不是追加重复数据。（已落地）
- 每个绑定可设置角色：文风参考、设定参考、结构参考、避雷参考。（已落地）
- AI 上下文中单独注入“参考书基础数据”，RAG 检索必须限制在当前书籍启用的参考书范围。（上下文、RAG 参考书索引/删除方法和导入 UI 调用已落地）

### 14.4 书籍级标签画像

书籍级模板新增分区和标签画像能力：内嵌标签库提供标准父标签/子标签，用户选择后才进入当前书籍 Truth，自定义标签用于覆盖特殊需求。

落地方式：

- 以 `docs/书籍级模板.txt` 的 19 个分区作为父标签权威列表。
- 以 `docs/父标签与子标签关系.txt` 生成内嵌只读标签库，保留父子关系、描述和 `全部` 归属。
- 书籍级模板 `1.3` 改为标签选择器：主分区、副分区、已选标签、自定义标签、标签备注。
- 标签栏内置搜索框，输入后按相似度检索，结果可滚动。
- 结果列表最后一行固定为自定义标签入口，保证特殊需求始终可录入。
- 保存书籍级模板后，已选标签写入 `tag_profile`，并同步到 Truth File 的“书籍标签画像”。
- 未选择的内嵌标签、搜索候选和未保存输入不进入 Truth。

### 14.5 RAG / Truth / 证据治理闭环

这部分是全书分析安全写回的底座：AI 可以提出建议，但只有可追踪证据和用户确认能让建议进入正式设定。

落地方式：

- 所有分析草案都记录 `evidence_summary`，并标出 `trusted/weak/missing`。
- `weak/missing` 字段只能显示为待确认或被阻止写回。
- RAG 结果按 `doc_type` 分区进入上下文，参考书和分析块不能伪装成正式设定。
- Truth File 只从已确认正式数据生成，草案只能提供 `candidate_truth_updates` 预览。
- 用户确认写回后同步刷新 Truth File 和相关 RAG 索引。

## 十五、PC 端认证与登录写入规划

> 本章节记录 PC 桌面端与 Web 书城之间的认证体系，以及 Web 端登录功能的完整实现，作为后续统一账号体系的工程参考。

### 15.1 现状分析

#### 15.1.1 PC 桌面端认证机制

PC 桌面端（PyQt6 写作台）当前**没有传统的用户名/密码登录系统**，与书城后端的认证完全依赖一个**可选的静态发布令牌**：

| 组件 | 说明 |
|------|------|
| **令牌名称** | `bookstore_publish_token` |
| **存储位置** | `data/ui_settings.json`，明文存储 |
| **传输方式** | HTTP 请求头 `X-Publish-Token: <token>` |
| **配置入口** | 设定 → 书城发布设置 → API地址 + 发布令牌（密码框） |
| **可靠性** | 可选填，不填也能发布；仅服务端配置了 `BOOKSTORE_PUBLISH_TOKEN` 时才校验 |

**代码路径**（[app_settings_export.py:L54-L94](file:///f:/项目/灵枢/novel_app/qt/app_settings_export.py#L54-L94)）：

```python
def _publish_current_chapter_to_bookstore(self):
    endpoint = f"{str(bookstore_api_url).rstrip('/')}/api/publish/chapter"
    publish_token = str(getattr(self, "bookstore_publish_token", "") or "").strip()
    headers = {"Content-Type": "application/json"}
    if publish_token:
        headers["X-Publish-Token"] = publish_token
    req = urlrequest.Request(endpoint, data=body, headers=headers, method="POST")
```

**AI API Key 认证**（独立于书城认证，[ai_client.py:L189-L192](file:///f:/项目/灵枢/novel_app/ai_client.py#L189-L192)）：

```python
headers = {
    "Content-Type": "application/json",
    "Authorization": f"Bearer {self.api_key}",
}
```

- AI API Key 使用 Windows DPAPI 加密存储
- 书城发布令牌**未使用**任何加密，明文存放在 JSON 文件中

#### 15.1.2 Web 书城认证体系

Web 前端已实现完整的用户登录系统：

| 层级 | 方案 | 文件 |
|------|------|------|

### 15.2 数据库表结构

```sql
CREATE TABLE IF NOT EXISTS users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    username TEXT NOT NULL UNIQUE,
    password_hash TEXT NOT NULL,          -- bcrypt($2b$12$...) hash
    is_author INTEGER NOT NULL DEFAULT 1, -- 1=作者 0=读者
    bind_reader_id INTEGER,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE IF NOT EXISTS auth_tokens (
    token TEXT PRIMARY KEY,               -- 64位 hex token
    user_id INTEGER NOT NULL,
    expires_at DATETIME NOT NULL,         -- 7天有效期
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
```

## 十六、下一代架构蓝图：五级分析与全实体共指消解

> 本章节来自 `docs/技术点.txt`，描述融合升级后的下一代长文本小说分析系统架构。当前落地方案的第一阶段（P0/P1）暂不实现完整实体共指消解和五级流水线，但本章节作为后续 P3/P4 迭代的目标蓝图。

### 16.1 整体流程概览

```
原始文本
  │
  ▼
【第一级】语义感知分块器（融合层叠划分）  ← 保留"重叠块+ID"理念，升级为语义级
  │  产出：带ID的语义块序列
  ▼
【中间层】全实体共指消解与向量知识库  ← 保留"人物代名融合+唯一ID+向量存储"，拓展为全实体
  │  产出：全局实体ID映射表、实体提及索引、实体向量库
  ▼
【第二级】块级深度分析（依赖中间层产出的实体ID）  ← 保留"初步分析人物、世界观"，升级为实体感知的分析
  │  产出：每块的实体属性、关系、事件片段
  ▼
```

### 16.2 第一级：语义感知的融合层叠分块

融合原则：保留重叠 10% 和每块独立 ID 的设计本质，但将机械切分升级为结构感知切分，避免切断语义。

- **切分层级**：优先按章/节/场景分隔符切分；在场景内部，以段落为原子，保证块边界不切断句子。
- **层叠与重叠**：相邻块之间的重叠窗口至少包含前后各 1-2 个完整句子，而非固定字节比例。这样既保留了信息的层叠融合能力，又确保了每个块内指代链的完整性。
- **元信息增强**：为每个块生成的 ID 附带：

```json
{
  "block_id": "b001-003",
  "chapter": 1,
  "scene": 2,
  "offset_start": 10420,
  "offset_end": 15980,
  "token_count": 1024,
  "prev_block_id": "b001-002",
  "next_block_id": "b001-004"
}
```

- **并行处理**：保留"一级多线程同步分析"的能力，每个块独立抽取元信息、切分和预处理可完全并行。

---

### 16.3 中间层：全实体共指消解与向量知识库

升级核心：将原设计的"人物代名融合+唯一ID+向量存储"拓展为覆盖人物、地点、组织、特殊物品、重要概念的全实体统一层。

#### 16.3.1 实体提及抽取（可与第一级流水线重叠）

每个块完成后立即进行轻量级实体提及抽取（人名、地名、组织名、代称等），产出局部实体列表。这一步不需要等所有块完成，可流式进行。

#### 16.3.2 全局共指消解与向量化

- **两级聚类**：先在章内局部融合生成候选实体 ID，再跨章全局合并。
- **向量相似度连接**：对每个实体提及及其上下文生成向量，进行相似度连接；结合规则（称呼、头衔、位置）确定是否属于同一实体。
- **全局唯一 ID 分配**：为最终每个实体分配全局唯一 ID（如 `ENT-P-001` 人物，`ENT-L-012` 地点），并建立别名映射表。

#### 16.3.3 向量存储形式

- 存储每个实体提及的嵌入（用于消歧和链接）以及实体概要嵌入（从所有提及聚合，用于检索）。
- 选用向量数据库（如 Milvus/Chroma），建立索引，支持"给定一段描述，查询最可能的实体 ID"。

#### 16.3.4 融合与增量合并

如果新出现的别名与已有实体产生高相似度，立即触发回溯审查，保证 ID 体系的持续一致性。

---

### 16.4 第二级：实体感知的深度分析

保留"分析人物、世界观等情况"的目标，但现在每个块的分析都直接引用中间层产出的全局实体 ID，分析内容更加精准。

- **输入**：原始块文本 + 该块内标注好的实体提及及 ID。
- **分析输出结构化片段**：
  - 人物：属性（外貌、性格）、当前状态、与其他实体 ID 的关系三元组。
  - 世界观：地点描述、规则系统、时间线事件、组织架构。
- **可溯源**：所有分析结果都带上 `entity_id` 和 `source_block_id`，为卡片生成提供可溯源的原子事实。
- **并行执行**：二级分析可以对每个块独立并行，因为它们共享的实体 ID 已是全局一致的。

---

### 16.5 三、四、五级卡片写入：事件驱动的流式生成

保留"在一二级分析完成的情况下同步对三四五级分析写入"的并行思想，但引入卡片管理器，消除严格的全局依赖，实现流式触发。

#### 16.5.1 卡片 Schema 严格 JSON 化

所有卡片统一遵循带版本的 JSON Schema，例如人物卡：

```json
{
  "card_type": "character",
  "entity_id": "ENT-P-001",
  "card_version": 3,
  "last_modified": "2026-05-21T10:00:00Z",
  "attributes": { },
  "relations": [ ],
  "source_chunks": ["b001-003", "b002-005"],
  "status": "stable"
}
```

#### 16.5.2 生成触发时机（打破全局屏障）

| 卡片类型 | 触发条件 |
|----------|----------|
| 人物卡（第四级） | 当一个实体的属性事实收集到足够置信度（如超过 3 个不同块的佐证），或实体被标记为"主要人物"时，立即触发人物卡生成/更新。不等全部分析结束。 |
| 世界卡（第三级） | 当某个地点或组织的描述片段累计到阈值，或出现新的世界观规则时，生成世界卡片。 |
| 书籍卡（第五级） | 监听"所有主要人物卡和核心世界卡均已生成"的事件后启动，汇总宏观主题和主线梗概。 |

- **并行写入控制**：不同实体的人物卡、世界卡可以完全并行生成。同一实体多次更新时，通过版本号乐观锁保证一致性，卡片管理器负责合并和冲突解决。

---

### 16.6 回溯检查机制：精准化与最小化重算

保留"遇到问题对所有 ID 进行回溯检查"的兜底策略，但明确触发条件和作用范围。

#### 16.6.1 明确触发条件

1. 向量聚类发现两个原本独立的实体相似度超过阈值且符合共指规则 → 需合并 ID。
2. 新实体提及无法链接到任何现有实体，但上下文显示可能是已知实体的别名 → 分裂或重新链接。
3. 人工审核标记出错误链接。

#### 16.6.2 轻量级回溯

- 维护一个实体 ID 的融合/分裂历史图，记录 `ENT-P-003` 由 `ENT-P-001` 和 `ENT-P-004` 合并而来等。
- 回溯时，只重算受影响实体的卡片，并自底向上更新引用它们的书籍卡。
- 所有卡片保留旧版本，方便对比和回滚，状态标记为 `stable` / `under_review` / `deprecated`。

#### 16.6.3 置信度机制

所有实体链接关系都带有置信度分数，低置信度的自动进入回溯审查队列，高置信度直接通过。

### 16.7 扩展性与工程优化

- **多书宇宙扩展**：实体 ID 前加入作品前缀（如 `BOOK_AZ::ENT-P-001`），向量库按作品分区。未来可跨书共指消解，直接复用整套流程。
- **LLM 调用优化**：一级抽取、二级分析、卡片生成本质是大量 LLM 请求，可引入批量异步、缓存相似块、要求 JSON 模式输出，降低成本并保持结构统一。
- **前端调试友好**：所有卡片中保留 `source_chunks` 和关键原文引用，方便人类回溯验证，也让大模型的生成更具可解释性。
