# 灵枢 · 项目抢救方案（2026-09）

> 依据：2026-09-18 全项目体检（后端 / 前端 / 构建-CI-测试 / 仓库卫生四线审计）。
> 性质：**修复型方案，不是重写方案**。主线技术栈 Vue3 + FastAPI + Electron 没有问题，问题在工程地基、结构债务与流程装饰化。
> 原则：先止血 → 再地基 → 再减法 → 再拆解 → 最后工程化。每个阶段有独立验收标准，做完一个才能开下一个。

---

## 〇、诊断摘要（为什么是这套方案）

体检结论：局部代码卫生好（零 console 残留、极低 TODO、Electron 安全基线规范、lingshu-app 有 26 个真实 vitest），但存在三类病根：

1. **装饰病**：CI 从未运行（无 remote）、覆盖率门槛从未被消费、依赖锁是脏环境 freeze、测试基线现在是红的且没人发现。
2. **叠罗汉病**：每个架构问题用新的一层去补而不拆旧的——db_bridge 粘合 13-Mixin 上帝对象、book_sync.py 1208 行弥合双库、cloud-admin 与 lingjing-app 双管理端、三份手写 ensure_column、两代打包体系并存。
3. **单机幻觉病**：硬编码账号 `001/12345678a`、测试直连生产站 `ling-shu.top`、打包依赖不入库的截图 PNG 和 .NET csc.exe——系统只在本机肌肉记忆上成立。

致命项（P0）：仅 2 个 commit 无 remote、1088 条未提交变更；`npm test` 当前必红；根 package.json 引用不存在的 admin-web；5175 端口冲突；lingjing 打包后必崩；全局单 SQLite 连接跨用户事务污染风险；token 明文+哈希双写；`require_ai_access` 等于 `require_login`（免费用户可无限烧服务端 AI Key）；全局人物 IDOR。

## 三、阶段 1：地基（第 2–3 周，工作量 1.5–2 周）

目标：**并发正确性 + 安全补丁 + 依赖收口。** 这是全方案技术含量最高的阶段。

### 1.1 安全执行漏洞四连修
- [ ] **token 明文双写**（`novel_app/bookstore/store.py:755-758`）：改造为只存 `token_hash`；存量数据写一次性迁移（对已有明文 token 计算 hash 后填充、删除明文列）；`store.py:2685` 的 `SELECT t.*` 改为只取哈希列。**先写"token 登录"的回归测试再动手。**
- [ ] **require_ai_access 名不副实**（`lingshu_api/dependencies.py:81-89`）：加入真实校验——每用户每日 token 上限（查 usage 事件表）+ 在途请求并发上限 + 账号状态检查；超限返回 429。同时处理 `ai_settings.py:327-335` 环境变量 Key 静默注入：要么对免费用户禁用服务端 Key 池，要么配额独立核算并记录 trace_id。
- [ ] **全局人物 IDOR**（`lingshu_api/routers/characters.py:156-190`）：`book_id` 为 0/None 时的归属校验改为必过（全局人物归属当前用户或显式共享表），无效即 403。
- [ ] **WS 爆破封禁**（`lingshu_api/ws/connection.py:93-94`）：`WS_AUTH_FAILURE_BAN_THRESHOLD` 默认值 0 → 5，并保留 env 覆盖。
- [ ] **Linux 明文 Key 落库**（`lingshu_api/services/ai_settings.py:141`）：去掉 `allow_plaintext_fallback=True`；无 keyring 环境改为用 `LINGSHU_MASTER_KEY` env 做 Fernet 对称加密（桌面 safeStorage 路径不变），彻底无密钥时启动报错并给文档指引。

### 1.2 SQLite 并发正确性（最高技术风险项）
- [ ] **换掉全局单连接**：`novel_app/database.py:174-213` 的 `check_same_thread=False` 单连接 → FastAPI dependency 每请求独立连接（`sqlite3.connect` 开销在小库上可忽略）+ `PRAGMA journal_mode=WAL` + `busy_timeout`。
- [ ] **事务语义修复**：`transaction()` 的"抑制 commit"改为 contextvar/线程本地实现，杜绝其他线程写入被并进当前事务；删除 `conn._connection.commit()` 这类绕锁提交。
- [ ] **锁收敛**：删除 WorkspaceDB `_write_lock`（保留一处写串行化即可），修正 `db_bridge.py:44` "仅迁移" 的失实注释。
- [ ] 写一个并发回归脚本：两个线程同时写不同书籍/章节各 N 次，断言互不污染、无 `database is locked`。

### 1.3 依赖收口（三轨 → 两轨）
- [ ] 删除 `requirements.lock`（脏环境 freeze，含 docker/altgraph 等 145+ 项，无任何流程消费它；对应删除 `test_core_modules.py` 里的相关断言）。
- [ ] `requirements.txt` 保持单一来源；用 `pip-compile`（或 uv）从它生成 `requirements.lock`（新语义：可安装的精确版本），CI 安装 lock 而非 dev 文件。
- [ ] 修正 dev 与主文件的 httpx 区间不一致；uvicorn 的 `<0.24` 放宽。
- [ ] `tests/` 对 aiohttp/requests 的依赖要么进 dev 依赖、要么删测试。

### 1.4 迁移机制（不引 alembic，做轻量版）
- [ ] 建 `novel_app/db/migrations/` 目录 + `schema_migrations` 版本表；现有 `ensure_column` / 66 个 CREATE TABLE 收敛为**一份** `ensure_column` 工具 + 按版本号的迁移脚本；`bookstore/models.py` 的第二份实现改为 import 同一工具。

## 七、不做清单（抢救期的纪律）

| 不做 | 理由 |
|---|---|
| 不整体重写、不换框架 | Vue3/FastAPI/Electron 主线健康，重写会把 5.8 万行业务知识归零 |
| 不加任何新功能 | 抢救期所有产能给地基；新功能会在旧地基上继续叠罗汉 |
| 不合并双库（暂） | 高风险大手术，先让播种逻辑收敛，阶段 3 后再评估 |
| 不全量 TS 化 | 收益/成本比低；只约束新文件 |
| 不升级 lingjing-app | 它的下场是被砍 |
| 不追求 lint 零告警洁癖 | 只清 110 个存量 + 防新增即可，不为 SIM105 之类重写逻辑 |
