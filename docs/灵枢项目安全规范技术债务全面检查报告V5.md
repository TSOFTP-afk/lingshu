#### V5-H01：WebSocket chat/review IDOR

- **文件**：`lingshu_api/ws/chat.py` 第 211-214 行、261-265 行；`lingshu_api/ws/review_ws.py` 第 60-61 行、96-99 行
- **描述**：`chat.py` 的 `_build_chat_context_prompt` 直接用 `book_id`/`chapter_id` 读取书籍数据（大纲、正文、人物卡等），不校验用户是否拥有该书。`review_ws.py` 的 `_run_review` 仅用 `chapter_id` 获取章节，不检查所有权。
- **攻击场景**：用户 A 发送 `{"type":"chat","payload":{"book_id": <用户B的书ID>}}` 即可读取用户 B 的完整书籍内容。
- **修复建议**：在 WS 处理器中增加 `check_book_owner(book_id, user)` 校验。

#### V5-H02：API world.py IDOR

- **文件**：`lingshu_api/routers/world.py` 第 19-30 行
- **描述**：`GET /api/workspace/books/{book_id}/world` 路由只检查书籍是否存在，不调用 `check_book_owner`。
- **攻击场景**：用户 A 请求 `GET /api/workspace/books/<用户B的book_id>/world` 即可获取用户 B 的世界观数据。
- **修复建议**：添加 `check_book_owner(book_id, user)` 调用。

#### V5-H03：WebSocket 消息无大小限制

- **文件**：`ws/connection.py:278`、`ws/analysis_v3_ws.py:45`、`ws/generation.py:58`、`ws/chat.py:74`、`ws/review_ws.py:39`
- **描述**：所有 WS 端点使用 `ws.receive_text()` 接收消息，未对消息大小做限制。攻击者可发送超大消息导致 OOM。
- **修复建议**：在 `receive_text()` 后增加长度检查（如 `MAX_WS_MESSAGE_SIZE = 1_000_000`），超限断开连接。

#### V5-H04：无每 IP 连接频率限制

- **文件**：`ws/connection.py:86-107`
- **描述**：`ConnectionManager.connect()` 检查了 IP 封禁和最大连接数，但没有每 IP 连接频率限制。攻击者可快速循环建立/断开连接。
- **修复建议**：增加滑动窗口频率限制（如每 IP 每分钟最多 10 次新连接）。

#### V5-H05：analysis_v3 路由无速率限制

- **文件**：`routers/analysis_v3.py` 全文
- **描述**：整个分析路由模块没有使用 `slowapi` 的 `@limiter.limit()` 装饰器。高消耗端点（如 `POST /analysis-v3/runs`）可被恶意重复调用。
- **修复建议**：为高消耗端点添加速率限制（如 `@limiter.limit("3/minute")`）。

#### V5-H06：Electron 30.x 已 EOL

- **文件**：`electron/package.json:87`、`lingjing-app/package.json:67`
- **描述**：Electron 30.x 基于 Chromium 124，已于 2024 年 12 月 EOL，不再接收安全补丁。
- **修复建议**：升级至 Electron 33.x+（当前 LTS）。

#### V5-H07：CI 工作流缺少权限限制

- **文件**：`.github/workflows/ci.yml:1-9`
- **描述**：工作流未设置 `permissions` 字段，默认拥有仓库写入权限。如果工作流被攻击者利用（如通过 PR 投毒），可能获得对仓库的写入权限。
- **修复建议**：添加 `permissions: contents: read`。

#### V5-H08：卡片写回 writeback_fields 无白名单

- **文件**：`novel_app/analysis/v3_writeback.py:45-74`
- **描述**：`validate_schema_gate` 仅校验 `writeback_target` 的必填字段，但 `writeback_fields` 可携带任意额外键值对，这些字段会被存入快照数据中。
- **修复建议**：对 `writeback_fields` 增加白名单过滤，仅允许已知字段。

#### V5-M01：心跳超时机制不完整

- **文件**：`ws/connection.py:148-163`
- **描述**：`ping_loop` 只发送 ping 但不检查 pong 响应时间。`last_pong` 字段存在但从未被更新（没有 pong 处理逻辑），也从未被检查。僵尸连接会一直占用 `connections` 字典。
- **修复建议**：实现 pong 处理逻辑，超时未响应则断开连接。

#### V5-M04：导出文件名 Header Injection

- **文件**：`routers/export.py:53-55`
- **描述**：`safe_name = book.get("title", "export").replace(" ", "_")[:40]` 仅替换空格和截断长度，未过滤双引号 `"`、换行符 `\r\n` 等特殊字符。如果书籍标题包含这些字符，可能导致 HTTP Header Injection。
- **修复建议**：对文件名进行更严格的过滤，移除所有非字母数字和中文字符。

#### V5-M08：卡片写回 name 弹性匹配可被利用

- **文件**：`analysis/v3_writeback.py:288-371`
- **描述**：人物和世界观的写回通过 `name` 字段进行匹配，找到同名条目则更新。攻击者可通过构造特定 `name` 值来覆盖已有条目的数据。
- **修复建议**：写回时增加实体 ID 校验，而非仅依赖 name 匹配。

#### V5-M10：CardCoordinator 无并发安全机制

- **文件**：`analysis/card_coordinator.py:50-127`
- **描述**：`CardCoordinator.run()` 方法没有加锁或事务隔离。如果同一 `book_id + run_id` 的卡片协调被并发调用，可能导致竞态条件。
- **修复建议**：为 `run()` 方法添加 `asyncio.Lock` 或数据库事务。

#### V5-M13：AI 并行调用无超时控制

- **文件**：`analysis/pipeline_v3_stages.py:365-408`
- **描述**：`_parallel_ai_extract_mentions` 和 `_parallel_ai_extract_facts` 使用 `ThreadPoolExecutor` 并行调用 AI，但 `future.result()` 没有设置 `timeout` 参数。如果 AI 服务挂起，线程将永远阻塞。
- **修复建议**：为 `future.result()` 添加 `timeout` 参数（如 300 秒）。

### 5.3 前端渲染安全

**关键结论**：当前项目**未使用 v-html**，不存在通过 v-html 渲染导致的 XSS 风险。

- 搜索 `lingshu-app/src/` 全部 `.vue` 文件，**零 v-html 使用**
- 唯一 `innerHTML` 使用位于 `StarGraphView.vue:76`，仅用于清空 DOM 容器（`el.innerHTML = ''`），无 XSS 风险
- SearchPanel.vue 的搜索高亮使用安全的 Vue 模板方式（`{{ }}` 插值自动转义）

**潜在风险**：如果未来在卡片数据展示组件中引入 `v-html` 来渲染 AI 生成的 Markdown 内容（如 `profile_text`、`outline_text`），AI 生成的文本可能包含恶意 HTML/JS 代码，构成存储型 XSS。建议在引入 `v-html` 前必须使用 DOMPurify 进行消毒。

- `PRAGMA foreign_keys = OFF` — 仅在 `admin_auth.py` 中用于管理操作，操作后立即重新启用
