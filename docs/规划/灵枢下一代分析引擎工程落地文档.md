## 1. 工程结论

灵枢下一阶段不应直接重写现有分析链路，而应采用“旧链路稳定运行 + 新链路 feature flag 灰度”的方式推进。

当前项目已经从 PyQt6 主界面迁移到 Vue/Electron/FastAPI 方向，因此原技术方向文档中提到的“PyQt6 抽屉视图”在落地时统一替换为：

- 前端：`lingshu-app` 的工作台右侧工具箱、设置中心、分析页签。
- 后端：`lingshu_api` 的 workspace/settings/analysis API。
- 核心算法：`novel_app/analysis` 新增 V3 模块，不直接破坏 `pipeline.py` 旧流程。
- 数据：继续使用 SQLite，新增 `analysis_*` 表，通过 `app_migrations` 做可重复迁移。

第一阶段的工程重点不是“让 AI 一次性读懂全书”，而是先把可追溯的数据底座搭起来：

1. 章节原文可稳定切分为语义块。
2. 每个块有 hash、版本、章节归属和字符范围。
3. 实体、提及、事实、卡片、探针都能追溯回原文证据。
4. 所有 AI 结果只进入草案层，正式写回仍必须走证据门禁与人工确认。

## 2. 当前基线

### 2.1 已可复用能力

| 能力 | 当前位置 | 落地方式 |
|---|---|---|
| 分块 | `novel_app/analysis/chunker.py` | 保留为兼容分块器，新建语义分块器复用长段落切分逻辑。 |
| 分析运行 | `novel_app/analysis/pipeline.py`、`store.py` | 旧流程继续可用，新建 `pipeline_v3.py`。 |
| 草案卡 | `card_builder.py`、`analysis_cards` | 扩展依赖关系，不直接替换旧卡片表。 |
| 证据门禁 | `evidence.py`、`diff_apply.py`、`writeback.py` | 保持为正式写回前唯一门禁。 |
| 数据库迁移 | `novel_app/db/schema.py` 的 `app_migrations` | 新表统一走迁移 ID，不做启动时破坏性变更。 |
| 本地 RAG | `novel_app/rag/qdrant_client.py` | 继续作为 JSON/本地向量集合适配层。 |
| 前端分析入口 | `lingshu-app/src/components/drawer/AnalysisTab.vue` | 扩展为“运行、实体、事实、卡片、探针、回溯”分区。 |

### 2.2 当前缺口

| 缺口 | 风险 | 工程补齐方式 |
|---|---|---|
| 分块粒度粗 | 章节级分析漏掉场景变化和伏笔演进 | 引入 semantic block，保留场景、句子重叠和 hash 复用。 |
| 没有提及级实体层 | 人物/地点/组织无法稳定追踪 | 新增实体主表、提及表、别名表和版本图。 |
| 缺少原子事实 | 卡片无法精确溯源 | L2 只产事实，不直接产正式卡。 |
| 卡片生成缺少事件协调 | 并发、重跑、依赖变更不可控 | 新增 `analysis_events` 和 `CardCoordinator`。 |
| 没有记忆分层 | 长文本上下文膨胀 | 对 fact 增加短期/长期、重要/稀释、基础/缓存三维分类。 |
| 没有主动一致性检查 | 伏笔、境界、关系容易前后矛盾 | 新增文章探针计划与执行结果表。 |

## 3. 落地原则

1. **Feature flag 先行**：新增 `analysis_pipeline_mode = legacy | v3`，默认 `legacy`。
2. **只读原文层**：分块、实体提及、事实抽取只能读章节正文，不直接写正式设定。
3. **草案优先**：AI 输出进入 `analysis_*` 草案/事实层，不直接改 `characters`、`world_entries`、`book_outline`。
4. **证据可追溯**：每个实体提及、事实、卡片、探针结果必须能定位到章节、block、quote。
5. **最小重算**：hash 未变化的 block 复用结果；实体纠错只重算受影响依赖。
6. **前端轻算法**：Vue 只展示、筛选、确认、触发任务，不承载实体合并和事实判断算法。
7. **可中断续跑**：所有后台阶段必须能记录状态、失败原因和重试入口。

## 5. 数据库迁移

### 5.1 迁移策略

- 新增迁移 ID：`analysis_v3_foundation`。
- 启动时自动创建新表和索引。
- 不修改旧 `analysis_runs`、`analysis_cards`、`analysis_blocks` 的语义。
- 新表均包含 `book_id`、`run_id`、`created_at`、`updated_at`。
- 所有 UID 使用可读稳定格式：`BOOK-{book_id}::ENT-P-000001`。

### 5.2 必须新增表

| 表 | 用途 |
|---|---|
| `analysis_entities` | 实体主表，存规范名、类型、摘要、置信度、状态。 |
| `analysis_entity_mentions` | 原文提及，存 quote、章节、block、字符范围。 |
| `analysis_entity_aliases` | 别名、称谓、误写、人工确认来源。 |
| `analysis_entity_edges` | 实体关系图。 |
| `analysis_entity_versions` | 合并、拆分、改名、人工纠错历史。 |
| `analysis_facts` | 原子事实和三维记忆分类字段。 |
| `analysis_events` | 卡片生成和回溯事件 outbox。 |
| `analysis_card_dependencies` | 卡片依赖的实体、事实、block。 |
| `analysis_backtrack_tasks` | 精准回溯任务。 |
| `analysis_probe_plans` | 探针计划。 |
| `analysis_probe_results` | 探针执行结果和一致性判定。 |
| `analysis_llm_cache` | LLM 阶段缓存。 |

### 5.3 索引要求

| 索引 | 目的 |
|---|---|
| `(book_id, entity_uid)` | 实体详情和依赖查询。 |
| `(book_id, run_id, block_uid)` | fact/mention 回查原文。 |
| `(book_id, chapter_id)` | 当前章节增量分析。 |
| `(book_id, content_hash)` | block 复用。 |
| `(book_id, subject_entity_uid)` | 实体时间线。 |
| `(book_id, status, priority)` | 事件与探针队列消费。 |

## 6. 五级流水线实施方案

### Phase 0：开关、迁移和最小壳

目标：让 V3 可以被调用，但默认不影响旧流程。

交付：

- `analysis_pipeline_mode` 配置项。
- `analysis_v3_foundation` 数据库迁移。
- `AnalysisPipelineV3.start_run()` 只创建 run，不执行 AI。
- API：`POST /api/workspace/books/{book_id}/analysis-v3/runs`。
- 前端分析面板显示 V3 开关、运行状态和失败原因。

验收：

- legacy 分析流程不回归。
- 新表重复迁移无报错。
- 无 AI Key 时也能创建 V3 run。

### Phase 1：L1 语义分块

目标：把章节正文切成可复用、可追溯的 semantic blocks。

实现：

- `semantic_chunker.py`
- 支持章节边界、场景分隔符、段落边界、句子边界、硬切 fallback。
- 每个 block 写入 `analysis_blocks`，并补充 `content_hash`、`structure_hash`、`pipeline_version`。
- hash 未变化时复用旧 block 的索引和下游结果。

验收：

- 10 万字书籍分块不切断句子。
- 每个 block 可定位回章节和字符范围。
- 同一正文重复分析 hash 稳定。

### Phase 2：实体提及抽取

目标：从原文中找出人物、地点、组织、物品、概念、世界规则提及。

实现：

- `mention_extractor.py`
- 规则抽取先行：书名号、引号专名、常见后缀、已有正式层种子。
- LLM 抽取作为增强，只输出 mention JSON。
- 写入 `analysis_entity_mentions`，低置信只进候选池。

验收：

- 无远程 AI 时规则提取可运行。
- LLM 输出伪造字符范围时被拒绝。
- quote 必须能在原文 block 中找到。

### Phase 3：实体共指和版本图

目标：把多个提及聚合为稳定实体，并支持人工纠错。

实现：

- `coreference.py`
- `entity_store.py`
- 章内聚类：同名、规范化同名、称谓链。
- 跨章合并：名称相似 + 别名显式 + 上下文相似 + 时间线不冲突。
- 前端支持合并、拆分、改名、添加别名。

验收：

- 每次人工操作写入 `analysis_entity_versions`。
- 合并/拆分不删除原始 mention。
- 可回滚到上一实体版本。

### Phase 4：L2 原子事实抽取

目标：把原文块和实体上下文转成可校验事实。

实现：

- `fact_extractor.py`
- 输入：block、候选实体、已有事实摘要、参考书上下文。
- 输出：属性、状态、关系、世界规则、事件、伏笔。
- 保存到 `analysis_facts`。
- 低置信或证据弱的事实只进入审查池。

验收：

- `subject_entity_uid` 必须存在。
- `quote_text` 必须通过 evidence gate。
- `confidence < 0.55` 不触发卡片。

### Phase 5：L3/L4/L5 事件驱动卡片

目标：事实达到阈值后自动生成世界卡、人物卡、书籍卡草案。

实现：

- `analysis_events` 作为 outbox。
- `card_coordinator.py` 消费事件并判断依赖。
- `card_generators_v3.py` 生成不同级别卡片。
- `analysis_card_dependencies` 记录卡片依赖。

验收：

- 同实体卡片生成串行。
- 依赖 fact/hash 变化后旧卡标记 superseded。
- 所有卡片正式写回仍走 `writeback.py`。

### Phase 6：精准回溯

目标：实体纠错、事实冲突、卡片证据失败时，只重算受影响范围。

实现：

- `backtrack.py`
- 从实体版本、mention、fact、card dependency 计算影响范围。
- 创建 `analysis_backtrack_tasks`。
- 回溯结果只产新草案，不自动覆盖正式层。

验收：

- 合并两个实体后，只重算相关 facts/cards。
- 正式库恢复必须由用户手动确认快照。

### Phase 7：三维记忆分层

目标：让事实进入短期/长期、重要/稀释、基础/缓存分类。

实现：

- `memory_classifier.py`
- `memory_window.py`
- `memory_compressor.py`
- 对 `analysis_facts` 写入 `memory_scope`、`memory_importance`、`memory_type`、`importance_score`。
- 基础记忆和伏笔永不压缩。
- 缓存记忆满足阈值后压缩为摘要 fact。

验收：

- 最近 N 章默认短期记忆。
- 伏笔事实从短期降级长期时保留完整 quote。
- 缓存压缩保留 source_fact_uids 引用链。

### Phase 8：文章探针

目标：主动验证伏笔回收、实体状态、世界规则和关系演变。

实现：

- `probe_planner.py`
- `probe_executor.py`
- `consistency_checker.py`
- 探针从长期记忆、基础规则、实体时间线生成计划。
- 结果写入 `analysis_probe_results`，不一致时创建回溯任务。

验收：

- 支持四类探针：伏笔回收、实体状态、世界规则、关系演变。
- 探针结果必须带 source/target evidence。
- 不确定结果进入人工审核，不自动写回。

### Phase 9：Vue 前端体验

目标：把新分析能力做成可用的创作工作流。

实现：

- 工具箱“分析”页新增 V3 运行概览。
- 实体页：列表、详情、别名、提及、合并/拆分。
- 事实页：按实体、章节、置信度、记忆分类筛选。
- 卡片页：草案、证据、依赖、写回按钮。
- 探针页：计划、结果、一致性评分、冲突对照。
- 回溯页：任务队列、影响范围、执行/取消。

验收：

- 普通用户默认看到摘要，不被 raw JSON 淹没。
- 技术诊断信息可复制。
- 危险操作都有确认。

## 8. LLM 工程规范

1. 每个阶段独立 `prompt_version`、`schema_version`。
2. 输入输出都要写入 `analysis_llm_cache` 的 hash key。
3. 模型输出必须 JSON parse + schema validate。
4. 禁止模型生成不存在的 `entity_uid`、`block_uid`、`fact_uid`。
5. 所有 quote 必须回查原文。
6. 超时、限流、格式错误都写入 run/event 状态。
7. AI 配置按用途读取设置中心的用途配置：
   - `book_analysis`：全书分析。
   - `review`：审查。
   - `detector`：AI 率检测。
   - `skills`：技能索引。

## 11. 风险控制

| 风险 | 具体表现 | 处理 |
|---|---|---|
| 共指误合并 | 两个同名角色被合并 | 低置信只候选；人工拆分；版本图回滚。 |
| LLM 成本过高 | 每章多阶段调用成本失控 | 规则先行、hash 缓存、只对重要块调用 LLM。 |
| UI 信息过载 | 用户看不懂实体/事实/探针 | 默认摘要视图，技术细节折叠。 |
| 数据膨胀 | facts/mentions/probes 快速增长 | run 清理策略、压缩事实、索引约束。 |
| 写回误伤正式设定 | AI 错误覆盖人物/世界观 | 所有正式写回必须证据门禁 + 人工确认。 |
| 打包体积增加 | 新依赖导致 exe 变大 | 新依赖先评估体积，优先标准库和现有依赖。 |

## 13. 最终验收标准

功能层：

- 百万字文本可以分阶段分析，支持中断续跑。
- 人物、地点、组织、物品、概念形成稳定实体表。
- 人物卡、世界卡、书籍卡都能追溯到原文事实。
- 实体纠错后只触发最小范围重算。
- 基础记忆永不压缩，伏笔事实长期保留。
- 文章探针能发现境界跳跃、关系变化缺铺垫、世界规则冲突。

工程层：

- 新旧分析流程可切换。
- 所有新增表可重复迁移。
- 所有 AI 输出有 schema 校验和证据回查。
- 前端每个阶段都有清晰状态、失败原因和重试入口。
- Electron PC 端打包后可离线打开工作台，并能使用本地 SQLite 数据。

## 14. 下一步建议

建议从 M0 + M1 开始，不先做 LLM 大模型深度抽取。只要 semantic block、hash、实体提及和证据回查先稳定，后面的共指、事实、记忆、探针都可以逐层叠加；反过来如果一开始直接做“全书理解”，会把 prompt、缓存、数据库、UI 和写回风险全部搅在一起，排查成本极高。
