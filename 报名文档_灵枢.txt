# 【学习工作赛道】灵枢 — 百万字级长篇网文 AI 写作工作台

> 标签：学习工作

---

## 1. 创意名称 + 创意介绍

### 创意名称

灵枢（LingShu）

### 想解决什么问题

长篇小说（百万字级网文）创作周期长达数月甚至数年，作者在后期极容易出现人物设定前后矛盾、伏笔遗漏、世界观逻辑崩塌等"设定漂移"问题，且百万字级的信息过载让作者难以高效查阅和维护已有设定体系。

### 为什么会想到做这个

网文作者每天需要产出数千至上万字，大脑同时承载几十个角色、上百条设定和数百个伏笔。传统工具（Word / 记事本 / 云笔记）只能做线性记录，无法智能审查，更无法帮作者主动发现"第3章说你左撇子，第87章却用右手提剑"这类的隐性矛盾。我希望能为创作者提供一款懂长篇、懂小说工程学的 AI 工作台。

### 大概是什么产品

一款本地优先的桌面端 AI 写作工作台（Electron + Vue 3 + FastAPI），支持大纲规划、正文续写、多维审查、全书分析、Truth File 管理、RAG 智能检索和多智能体协作流水线。

---

## 2. 目标用户及痛点

### 面向哪些用户

长篇网络小说作者，尤其是百万字级别的连载创作者（网文作者、轻小说作者、同人作者）；同时管理员可通过灵镜管理台管理账号与作品。

### 在什么场景下使用

- 日更码字时，用 AI 续写/润色辅助提升效率
- 新增角色或新章节时，用 Truth File + RAG 快速检索已有设定，避免矛盾
- 阶段性复盘时，运行 V3 全书分析引擎，扫描全书的设定一致性问题、伏笔回收状态、实体关系变化
- 作品准备出版/完本时，用审查引擎进行 12 维度全面审计

### 当前痛点（没有灵枢时）

- 设定散落在脑袋、聊天记录、散乱的文档里，查一个角色信息可能翻几十个文件
- 伏笔写下就忘，回收率低，读者吐槽"挖坑不填"
- 写到后期自查设定矛盾（如年龄、时间线、人物关系）极度耗时，几乎不可能人工完成百万字全文审查
- AI 辅助工具零散割裂——续写用一个工具、纠错用另一个、审查再换一个——缺乏统一工程化管理
- 数据安全担忧——把百万字原稿上传到第三方 AI 平台存在隐私风险

## 3. 价值与意义

### 效率提升

- V3 分析引擎可在数分钟内完成百万字全文的语义分块、实体共指消解、原子事实抽取和记忆分层，这是人工数月都无法完成的工作量
- 12 维度审查引擎 + 26 条内置审计规则，自动检测人物一致性、时间线矛盾、世界观规则冲突等，把"排查矛盾"的时间从几周压缩到几分钟
- 文章探针机制可主动追踪伏笔生命周期，自动标记"已铺垫-未回收"的伏笔，提升作品完整度
- 多用途 AI 配置（9 种用途独立模型配置）让不同任务用最合适的模型，降低 Token 成本和等待时间

### 社会价值

- 降低长篇创作门槛，让更多有故事想法的人能持续写到完本，促进网文生态的内容繁荣
- 本地优先的数据架构设计（正文和设定默认不离开用户设备），尊重创作者的数据主权
- 用结构化 AI 工具替代"裸用大模型"，让创作者更专注于故事本身而非工具配置，回归"人写故事、AI 做工程辅助"的创作本质

## 4. 核心机制与差异化优势

> 为什么灵枢和市面上已有的写作工具从根本上不同

现有工具（Notion / Obsidian / Scrivener / 各类 AI 续写插件）的共同局限是"做了笔记和文本，却没有理解故事"。灵枢的核心差异在于它构建了一条完整的**小说工程学分析链路**，以下是灵枢区别于所有现有方案的关键机制：

---

### 机制一：V3 九阶段全书分析管线

> 不是"搜索关键词"，而是"理解设定"

现有工具最多能做到：关键词全文搜索、标签归类、手动关联。当你想查"主角获得神剑后实力变化的全过程"，你需要逐个章节翻找、自己拼凑。

灵枢的 V3 管线用一条 **9 阶段自动化流水线**替代了这个过程：

| 阶段 | 名称 | 能力 |
|:---:|------|------|
| 1 | 语义感知分块 | 不按字数硬切，识别小说特有的"场景切换 / 时间跳跃 / 视角转移"，将百万字切分为语义完整的分析块 |
| 2 | 实体提及抽取 | 从文本中自动识别出人名、地名、组织名、道具名等所有"实体被提及的位置"，精确到段落和句子 |
| 3 | 两级共指消解 | 将"张三 / 张老师 / 他 / 那个白衣青年 / 青云剑尊"归一化为同一个实体（NLP 高难度任务，灵枢在网文场景做了定向工程化） |
| 4 | 原子事实抽取 | 抽取不可再分的基本事实，如 `张三→获得→青云剑→第23章→置信度0.92` |
| 5 | 事件驱动卡片生成 | 将零散事实自动聚合成"人物卡 / 世界观卡 / 事件卡"，每张卡片附完整证据链 |
| 6 | 向量索引 | 所有分析结果向量化存储，支持语义级检索（搜索"主角的第一次战斗"而非只能搜"战斗"两个字） |
| 7 | ARS 记忆分层与压缩 | 四维评分后自动分为短期记忆（近3章）和长期记忆（全局），对长期记忆进行摘要压缩 |
| 8 | 文章探针与一致性检查 | 自动生成探针问题，在事实库中交叉验证——发现"第30章左撇子→第87章右手提剑"这类隐性矛盾 |
| 9 | 回溯任务与证据门禁写回 | 对不一致内容生成修正任务，经 Schema Gate + 自动快照写回正式设定表，可追溯可回滚 |

**对比传统工具**：Word / Notion / Obsidian 只能做"线性记录 + 手动搜索"，灵枢做的是 **"自动理解文本 → 抽取事实 → 发现矛盾 → 修正回写"**的完整闭环。

---

### 机制二：AI/规则双引擎 + 自动降级

> 离线可用，上线更强

大多数 AI 写作工具是"纯在线 AI"方案——没有网络就没有分析能力，且所有数据必须上传到云端。

灵枢在每一个分析阶段（提及抽取、共指消解、事实抽取）都实现了**双引擎架构**：

- **AI 引擎**：连接大模型时，使用 LLM 进行高精度分析
- **规则引擎**：断网或 AI 失败时，自动降级到本地规则引擎（基于正则、TF-IDF、规则模板的启发式系统）
- **回退策略**：AI 返回空结果或异常时自动 fallback 到规则引擎，并在审计日志中记录引擎类型（`ai` / `rule` / `rule_fallback`）

**实际意义**：

- 灵枢的核心分析能力离线可用（规则引擎不依赖网络）
- 接入 AI 时获得更高精度，但不会因网络波动丢失所有能力
- 用户拥有选择权——是否让 AI 参与分析由用户决定（`use_ai` 参数）

---

### 机制三：ARS 四维记忆分层系统

> 解决长文本 AI 的上下文窗口问题

GPT-4 / Claude 等大模型的上下文窗口虽然越来越大，但对于"百万字小说、数百章、持续数月"的创作场景，粗暴地把所有内容塞进 Prompt 既不经济（Token 成本爆炸）也不有效（模型注意力被稀释）。

灵枢的 ARS 记忆系统对每个事实进行**四维评分**：

| 维度 | 权重 | 含义 |
|:---|:---:|------|
| 叙事权重（Narrative Weight） | 0.30 | 该事实涉及的情节在当前全局故事中的比重 |
| 实体中心度（Entity Centrality） | 0.25 | 关联的角色/道具/势力在故事网络中的连接数量 |
| 新颖性（Novelty Factor） | 0.25 | 刚引入的新信息 vs 已反复出现的旧信息——越新越高 |
| 因果影响力（Causal Impact） | 0.20 | 该事实对后续情节的影响链长度 |

**分层策略**：

- `score ≥ 0.70` → 重要记忆，始终保持全文可检索
- 近 3 章 → 短期记忆（完整保留、不压缩）
- 3 章以前 → 长期记忆（`world_rule` / `state` 类型永不压缩；`event` / `relation` 压缩为摘要）
- TTL 90 天 → 超过 90 天未再次出现的事实自动标记衰减

**实用价值**：当作者在第 300 章使用 AI 续写时，灵枢自动把 **前 3 章完整记忆 + 全局重要设定 + 压缩后的历史事件摘要**一起注入 Prompt，而不是无脑塞入 300 章全文——既省钱，又比"只给最近几章"的方案精准得多。

### 机制四：文章探针与自动回溯

> 不只是"发现问题"，而是"定位问题 + 给出修正方案"

现有审查工具（语法检查、AI 概率检测）的典型模式是："这段可能有问题"——但不说是什么问题、在哪引入的、怎么修。

灵枢的探针机制更进一步，形成了完整的**三阶段闭环**：

1. **探针规划器（ProbePlanner）**：基于已有事实库自动生成探针问题，每个探针是一个待验证的一致性断言。例如"角色 A 的年龄在第 5 章和第 210 章是否一致？"、"伏笔 B（第 32 章提及的神秘信件）在后续章节中是否已回收？"

2. **探针执行器（ProbeExecutor）**：在事实库中检索证据，给出 `一致 / 不一致 / 需人工复核` 三种结果。

3. **回溯规划器（BacktrackPlanner）**：对不一致的探针结果，自动规划回溯任务——定位原始文本位置、标记问题类型（矛盾/遗漏/逻辑断裂），让作者直接跳转到问题源头。

整个过程中，所有分析结果文件（事实 / 实体 / 卡片 / 探针结果）都存储在本地 SQLite 数据库中，数据主权完全归作者所有。

---

### 机制五：多智能体编排流水线（AgentGraph）

> 不是"一问一答"，而是"规划 → 写作 → 审计 → 修订"的工程化流水线

市面 AI 写作工具的主流模式是"你给 Prompt → AI 吐一段文字"，相当于雇了一个只有短期记忆的枪手——上一章的设定下一章就忘了。

灵枢的 AgentGraph 把 AI 写作拆解为一个**可控的 4 步串行流水线**：

| 步骤 | Agent | 职责 |
|:---:|------|------|
| 1 | **PlannerAgent**（大纲拆解） | 接收本章大纲，拆解为可执行的写作计划（情节节点、节奏控制、信息密度目标） |
| 2 | **WriterAgent**（正文写手） | 基于 Plan + Truth File（7维设定）+ Skills（用户自定义风格指令）+ 参考书片段，生成章节草稿 |
| 3 | **AuditorAgent**（一致性审计） | 将草稿与 Truth File 交叉比对，按 26 条内置审计规则（覆盖 12 个维度）检出问题 |
| 4 | **ReviserAgent**（修订润色） | 根据审计发现修订正文，输出最终版 |

**关键设计**：

- 每步之间可取消（cancel event），作者可随时中断流水线
- 最终裁决分数化（0-100）+ 三级判定（`approve` / `revise` / `reject`），作者不会被"AI 默默改坏"
- 多用途 AI 配置：Planner 用推理能力强的模型、Writer 用文笔好的模型、Auditor 用逻辑能力强的模型——不同任务独立配模型，降低 Token 成本

---

### 机制六：Truth File 七维设定体系 + 自动构建

大多数创作工具让作者手动创建"设定文档"，但百万字下来，人物表、世界观、伏笔清单的维护本身就是巨大的工作量，多数作者写到一半就放弃了。

灵枢的 TruthManager 管理 **7 个核心设定文件**：

| 文件 | 内容 |
|------|------|
| `current_state.md` | 当前故事状态（角色位置、状态、当前持有物） |
| `particle_ledger.md` | 关键道具账本（获得时间、持有者变化、最后一次出现） |
| `pending_hooks.md` | 待回收伏笔清单（已铺垫但尚未回收的伏笔自动汇总） |
| `chapter_summaries.md` | 章节摘要（自动生成，非人工梳理） |
| `subplot_board.md` | 支线看板（每条支线的起点、转折点、当前状态） |
| `emotional_arcs.md` | 情感弧光（主要角色的情感状态变化轨迹） |
| `character_matrix.md` | 人物矩阵（角色关系、立场、能力变化全景图） |

**关键差异**：这 7 个文件不是让作者手写的，而是通过 `build_all()` 方法从数据库自动拼装——数据库中有哪些人物、哪些章节、哪些关系，TruthManager 自动组织为结构化的 Markdown 文件，每次分析或续写时都会刷新。

这意味着：作者不需要单独维护一份设定文档——你在创作的同时，灵枢在后台持续更新设定。**设定漂移的主要原因"设定文档和正文脱节"从根本上被解决了。**

---

### 机制七：写回证据门禁（Schema Gate + 自动快照）

AI 分析的结果不能"直接写入设定表"——如果 AI 出现幻觉（虚构了一个不存在的人物、误判了关系），直接写回会造成数据污染。

灵枢的写回流程设了**两层门禁**：

1. **Schema Gate**：验证 `writeback_fields` 中包含目标表的必填字段（人物必须有 `name`，世界观必须有 `name` + `category`），杜绝畸形数据入库。
2. **自动快照**：每次写回前自动创建 `analysis_apply_snapshots` 记录，可随时回滚到写回前的状态。

这在现有 AI 写作工具中是独一无二的——大多数工具是"分析完就结束了"，灵枢是 **"分析 → 门禁校验 → 写回 → 可回滚"**。

---

### 机制八：多用途独立 AI 模型路由

市面工具通常只能配置一个全局 AI 模型，所有任务共用一个模型。

灵枢支持 **9 种独立用途各自绑定不同的模型**：

```
生成 / 润色 / 纠错 / 审查 / AI检测 / 对话 / 实体抽取 / 事实抽取 / 共指消解
```

每个用途可以独立选择 API Provider（OpenAI / DeepSeek / 本地模型等）、模型名、temperature、max_tokens，通过 `model_router` 在运行时动态分发。

**实用价值**：作者可以用 DeepSeek（便宜+逻辑好）做审查和分析，用 Claude（文笔好）做正文润色，用 GPT-4o-mini（快+便宜）做日常对话——大幅降低 Token 消耗，同时不让"省钱"牺牲各环节的质量。

---

### 机制九：本地优先 + 多端安全管理

数据安全方面，灵枢的做法不是"告诉我们你的数据很安全"，而是**"数据默认不出你的设备"**：

- 正文和设定默认只存在本地 SQLite 中，云端仅用于账号授权和可选手动同步
- 管理端（灵镜管理台）使用 HMAC 签名（`X-Client-KeyId` + `X-Client-Ts` + `X-Client-Sig`）+ 密钥文件（`.lingshu-key`）双重认证，token 与普通用户 token 物理隔离
- Electron 桌面壳使用 `safeStorage` 加密存储敏感密钥，safeStorage 不可用时拒绝明文保存
- AI 调用虽然是远程的，但可通过环境变量控制 API Key，且分析中间结果（`facts` / `entities` / `cards`）全部本地存储
